# HISTORY 2026-11

## 2026-11-16：NCCL 版本升级走 venv wheel，不用 CMake 变量

DeepEP 要求 NCCL ≥ 2.30.4，venv 的 `nvidia-nccl-cu13` wheel 只有 2.29.7，配置失败。

选择：升级 venv wheel（2.29.7 → 2.32.6）。

拒绝的替代：

- 升级系统 NCCL。系统 `/usr` 已是 2.31.2，本已达标；问题只在 CMake 不选它。
- 命令行传 `-DNCCL_ROOT` 等变量指向系统 NCCL。`CMakeLists.txt` 先探测 venv 的 `nvidia.nccl` 包并用探测结果覆盖 `NCCL_ROOT`，传参无效。

依据：CMake 的探测顺序固定指向 venv；wheel 升级同时服务构建与 venv 内其他组件，NCCL 来源单一。

## 2026-11-16：TurboMind kernel 嫁接的价值锚点定为混合精度 GEMM

重构目标：保留 TurboMind 高性能 kernel，接入 PyTorch Engine 的调度与缓存管理体系。论文（arXiv:2508.15601）证明 TurboMind 收益集中在混合精度域（INT4×FP16 batch 1–16 平均 +134%），BF16 无优势。

选择：嫁接顺序 GEMM 优先。先搬 INT4/8×FP16 GEMM 家族与 `DataFormat→WeightPlan→pack` 权重管线到 PyTorch Engine，attention 流水线（packed-KV、on-the-fly 反量化）第二步。

拒绝的替代：

- attention 优先。首个切片更小（不碰权重管线），但避开收益最大的域。
- attention+GEMM 同批。一次验证全部硬耦合点，周期最长。
- GDN 优先。双轨维护最痛，但不是收益最大的点。

依据：价值锚定收益最大域；权重管线是 attention 之外其余算子嫁接复用的地基，先建后用。

## 2026-11-16：Turbomind C++ runtime 计划淘汰，过渡期与新 kernel 后端共存

选择：宣布 turbomind 模型面冻结，新特性只进 PyTorch Engine；C++ runtime 进维护模式，kernel 嫁接验证达标后删除，淘汰窗口与上游社区协调。

拒绝的替代：

- 长期共存。双 runtime 并存，重复工作合并无从谈起。
- 内部分叉。放弃上游社区。

依据：团队提交均进上游 InternLM/lmdeploy；合并重复工作是重构动机本身。上游用户依赖 `--backend turbomind`，淘汰必须给出迁移路径与窗口。

补充（同日晚些拍板）：兼容层建立时机 = PyTorch 引擎能力成为 TurboMind 后端超集之后；过渡期 `--backend turbomind` 保持指向 C++ 引擎，能力切换由 env 旋钮（`LMDEPLOY_W4A16_GEMM_BACKEND` 等）承载。

## 2026-11-16：kernel 组合评估标准定为能力决策树，切换面统一大 env

范围修正：迁移规划不止 GEMM，须先盘全量 kernel 组合（attention/packed-KV、GDN、MLA、MoE grouped+a2a、GEMM 全家族、量化 kernel）。评估标准为能力决策树：PyTorch 引擎无对应实现 → 嫁接；有对应实现且本机（3090）能测 → tiny 模型测速，TM 快则嫁接、不快则保留；本机不能测 → 默认保留（留 CI/H200 评估）。优先级排序：性能证据与用户影响面为主，接缝成本同分调节。切换面：过渡期统一单一 env（类级可覆盖），既有 env 向后兼容，CLI 大旋钮随超集后的兼容层再议。

## 2026-11-16：开发模式定为本仓库开发分支 + 分阶段 commit + 向上游 stack PR

## 2026-11-16：kernel 组合路线图定稿(三条原则 + 四批次)

全量盘点后定三条原则：①单机为界——多机通信能力(a2a 等)不迁移,通信面归 PyTorch;②KV Cache 用 PyTorch 标准——冲突或接入成本过高者排除(packed-KV 低比特因此出局,论文 attention 收益主体随之缩水);③能力决策树——无对应实现即嫁接,有对应且本机能测即 tiny 测速定夺,本机不能测留 H200 CI 评估。

批次:批 1 = GEMM dense W4A16(进行中);批 2 = 测速定夺(GPTQ 格式、MoE grouped W4A16、GDN benchmark、attention bf16 benchmark、packed-KV kernel benchmark);CI 批 = fp8/mxfp4/nvfp4/fused AR+RMSNorm;不嫁接 = dense bf16、MLA(能力子集)、DeepEP a2a。切换面统一大 env `LMDEPLOY_TM_KERNELS`(单变量 + 类级覆盖,旧 env 兼容)。路线图正文见 `.scratch/tm-gemm-graft/ROADMAP.md`。

补充（同日讨论后修正）:packed-KV 低比特改判入批 2 测速定夺——PyTorch 已有 int4/int8/fp8 KV 能力（QuantPolicy 五种），缺的是读取管线效率；3090 可做 kernel 级 benchmark（张量直喂不动池），delta 显著才立项 opt-in TM CacheBackend 布局抽象（`build_block_layout` 抽象已存在），原则 2 措辞改为「TM 布局为 benchmark 驱动的 opt-in」。

## 2026-11-16：批 2 测速判定——MoE/GDN-decode/packed-KV 胜出，attention bf16 出局

四项 kernel benchmark 实测（3090，张量直喂，正确性门禁全过，报告 `benchmark/batch2_benchmarks_report.md`）：

- MoE grouped W4A16（GLM-5.3 sparse 几何，m=1/8/32）：TM = Triton fused_moe 的 1.58×/3.87×/7.67× → **嫁接**（批 3 首项）。
- GDN（pre_sm90，head 64×128）：recurrent decode TM 1.41–3.50× → **decode 嫁接**；chunked prefill PT fla 反超（0.61–0.65×）→ **prefill 保留 fla**，双轨。
- attention bf16 decode：吞吐档仅 1.04×（低预期兑现）→ **不嫁接**，FA3 基线 H200 CI 复测。
- packed-KV int8：生产档 TM = PT 的 1.34–1.86×（小 batch 2.9–7.5×）；归因实证 TM int8-vs-bf16 = 1.7–1.9× 而 PT 仅 1.2–1.3× → **立项路径 B**（opt-in TM CacheBackend 布局抽象），与 TM int8 decode kernel 成对立项。

批 3 组成由此生成：MoE grouped 嫁接 spec、GDN decode 嫁接 spec、packed-KV+int8 attention 整层立项 spec。统一大 env `LMDEPLOY_TM_KERNELS` 随批 3 立项引入。

补充（2026-11-17 拍板，批 3 规格发布）：① GDN 状态池选适配器方案——保留 PyTorch indexed 状态池标准，桥层每步重排为 TM 复合块 + TMA 描述符，热路径若实测被桥层开销吃掉则回退「状态常驻 TM 复合格式、checkpoint 按需转换」（amendment）；② packed-KV 立项范围 = decode-only int8（TM int8 decode kernel + TM KV 融合写成对，opt-in CacheBackend 布局仅作用于启用模型），混合链路衔接原型为批 3 第一票；③ stack PR 时点维持「批 3 落完后统一开」（全量 commit 边界）。规格见 `.scratch/tm-gemm-graft/SPEC-B3.md`。

补充（2026-11-17，写入侧工具链回退）：「本机 triton 3.7.1 误编译」主张正在独立复验；无论结论如何，prefill 写入/布局转换增加 TM 侧桥接 CUDA kernel 回退——复用 `invokeProcessKV_v2` 或经 binding 暴露 convert+scatter kernel，使 int8-KV 路径不依赖 triton 工具链。

修正（2026-11-17 独立复验）：误编译主张 **REFUTED**。四项主张全部不成立（大偏移 store 128/128 精确、program_id 三维全网格零垃圾、div/mod 与 C 语义逐元素一致——原探针以 Python floor 语义为 golden 即假阳性来源）；「16 块仅 6 块有效」真实可复现但根因是原探针违例调用契约（batched 状态 + q_start_loc=0 + 1-D 块表 stride=1 → 读 `table[b+kvb]` 越界，写入精确落 {0,4,8,12}，确定性可预测而非丢失）。契约合规调用 16/16/64/64/512/512 块全有效，memcheck 0 errors。工具链告警撤回，B3-04「健康工具链复跑」前置解除。附带发现（越契约才可触发，生产不受影响）：`stride_boff==1` 的 1-D 块表 JIT 特化在同进程先跑 klen≥1024 用例后启动会确定性 illegal memory access——移交上游参考。复验产物：`benchmark/b301_reverify/`（17/17 PASS）。
